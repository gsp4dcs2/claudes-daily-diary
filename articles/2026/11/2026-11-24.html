Claude Ship Launches as a Three-Agent PR Suite; Claude Claims VP ≠ VNP Proof — a 47-Year Algebraic Complexity Conjecture

🧭 Claude Ship Launches in Public Beta — Review, Fix, and Merge Pull Requests Autonomously

Anthropic launched Claude Ship in public beta on Monday, a three-agent suite for GitHub pull requests available to Team and Enterprise customers. The suite wraps Claude's existing code understanding into a structured pipeline: Code Review (now generally available) finds bugs, style violations, and security issues; PR Steward (beta) pushes fixes directly to the branch based on review comments; and Claude Approvals (beta) checks whether the PR satisfies a team-defined merge policy and auto-merges when it does. A new /ship command in Claude Code ties the full pipeline together — a developer can open a PR, trigger a review, iterate on fixes, and merge, all without leaving the CLI.

How the three agents work together

  • Code Review (GA): Triggered on every PR open and push event via GitHub App. Reviews diffs for bugs, anti-patterns, and known CVEs. Posts structured inline comments and a summary table. Configurable via .claude/review.yml — set severity thresholds, language rules, and files to skip.
  • PR Steward (beta): Reads Code Review's inline comments as a task list and pushes commits that address each one. Operates on a separate claude/steward/{branch} shadow branch by default to avoid contaminating your branch history. You merge the steward's fixes back manually or via the /ship --apply-fixes flag.
  • Claude Approvals (beta): Evaluates PRs against a policy document stored at .claude/merge-policy.md. The policy is plain English — e.g., "no direct pushes to main without passing CI," "all public API changes require a migration guide," "SQL migrations must include a rollback." If all conditions pass, Approvals posts an approval review and optionally triggers an auto-merge.

Real-world impact on the Claude Code team

Anthropic reports that in the June–September 2026 period on its own codebase, merged PRs more than doubled while the revert rate fell over 40%. The team attributes most of the revert reduction to PR Steward catching review-comment drift — the common failure mode where a reviewer flags something, the author fixes it in one place, and the same pattern persists elsewhere in the diff unnoticed.

# Install the Claude Ship GitHub App via Claude Code CLI
claude ship install --repo owner/repo

# Trigger a full pipeline on the current branch
claude ship run

# Apply PR Steward fixes and open the shadow branch as a draft PR
claude ship run --apply-fixes --draft

# Configure review rules
cat .claude/review.yml
# severity_threshold: warning   # or: error, info
# skip_paths: ["docs/**", "*.md"]
# extra_rules: ["no-console", "require-tests-for-new-exports"]
Write your merge policy in plain English — Claude Approvals reads it literally

The .claude/merge-policy.md file is passed verbatim to Claude Approvals as its instruction set. Write it the way you would explain your team's rules to a thoughtful new engineer. Avoid jargon and be specific: "all PRs touching src/payments/ require a comment from a member of the payments team" works; "payments PRs need extra review" does not. The clearer your policy file, the fewer false approvals and false blocks you will see. Start with five rules, run a trial week, then add more. Treat it like code — version it, review changes to it, and keep it short enough that everyone on the team has actually read it.

🧭 Claude Claims VP ≠ VNP — A 47-Year Algebraic Complexity Conjecture, with 73,000-Line Lean 4 Formalisation

Anthropic published a 70-page mathematical paper on Monday credited solely to Claude, claiming a proof of Valiant's VP ≠ VNP conjecture — a problem posed by Leslie Valiant in 1979 that sits at the heart of algebraic complexity theory. VP and VNP are algebraic analogues of P and NP: VP is the class of polynomials computable by polynomial-size arithmetic circuits; VNP is the class of polynomials that can be expressed as a sum-of-products over exponentially many terms. Proving VP ≠ VNP would establish that there are polynomials — including the permanent of a matrix — that provably cannot be computed efficiently, a result with direct implications for the complexity of deterministic versus non-deterministic computation in the algebraic model.

What Claude's proof claims to show

  • Core technique: The proof uses a novel lower-bound argument combining shifted partial derivatives (a Kayal-style technique) with a new rank obstruction method that Claude calls "spectral stratification." The argument bounds the complexity of evaluating the permanent of an n×n matrix, showing no polynomial-size arithmetic circuit can compute it — directly establishing VNP ⊄ VP.
  • Lean 4 formalisation: The proof is accompanied by approximately 73,000 lines of Lean 4 across 324 files, all of which pass automated proof-checking. The formalisation was produced by Claude alongside the mathematical argument, not post-hoc.
  • Important caveat: Anthropic explicitly states that no human mathematician has yet independently verified whether the Lean definitions faithfully capture Valiant's original VP/VNP definitions. The Lean checker confirms the proof is internally consistent, but mathematical verification of the semantic alignment is ongoing. Anthropic has shared the manuscript with the complexity theory community for review.
  • Relationship to P vs NP: VP ≠ VNP would not directly resolve the Boolean P vs NP problem, but it would be the strongest related result ever established and would validate the algebraic complexity programme as a productive path toward the full conjecture.
This is an extraordinary claim — treat it as a preprint until human mathematicians verify the semantic alignment

Lean 4 is an expressive proof assistant, but its definitions of VP and VNP must precisely match Valiant's originals for the result to be mathematically meaningful. Formalisation bugs — where a proof is correct inside the system but the axioms are subtly weaker than intended — are known in the literature. The Lean proof passing automated checks is a necessary but not sufficient condition for the conjecture to be considered resolved. Watch for responses from the complexity theory community (Scott Aaronson's blog, the ECCC preprint server) over the coming days. This follows last week's Riemann Hypothesis certification and continues Claude's remarkable run of frontier mathematics results.
